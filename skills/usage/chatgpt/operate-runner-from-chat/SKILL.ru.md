# Управление Runner из обычного ChatGPT через зарегистрированный слот

> Публичная копия скила из канонической библиотеки владельца. Действующий протокол и разрешения определяются установленным Runner; копирование файла не устанавливает и не активирует скил.

Канонический английский оригинал — [SKILL.md](SKILL.md). Перевод предназначен владельцу и не является отдельным установленным скилом.

Используйте, когда пользователь явно просит обычный ChatGPT выполнить конечный запуск/тест через Runner, проверить статус, отменить запрос или повторно доставить результат. Исполнение происходит локально в Runner; чат только составляет команду и читает подтверждения. Это не путь Udot для нескольких этапов и не Scheduled Capsule Chat. Чтение репозитория или скила само по себе не разрешает запуск.

Для явного поручения передать пакет используйте [deliver-handoff-to-runner](../deliver-handoff-to-runner/SKILL.ru.md): там описаны загрузка, зарегистрированный target и терминальная доставка, а порядок работы со слотом — ниже. `DELIVER_HANDOFF` должен поддерживаться выбранным установленным Runner; локальный файл скила не доказывает развёртывание. Эта операция не исполняет код и не требует полей source/task/execution.

## Действующий протокол
Сначала прочитайте одну согласованную текущую ревизию [операционного скила Runner](../../../v2/operate-runner-v2/SKILL.md), [инструкций v2](../../../../docs/V2_OPERATIONS.md) (отправка и результаты) и [схемы mailbox](../../../../schemas/v2-mailbox.schema.json). При существенном различии проверяйте установленную версию и подтверждённые возможности: исходники preview, примерные ID и merge не доказывают развёртывание. Если поведение расходится с протоколом, остановите зависящее действие. Это точка входа для ChatGPT, а не новая самостоятельная копия протокола.

## Одна конечная отправка в слот
1. Найдите реальные зарегистрированные ID раннера и проекта и точный транспорт: GitHub **репозиторий + ветка + путь командного файла** либо Docs **document ID + tab ID**. Для исполнения также определите задачу, разрешённые ОС/режим/профиль/лимит времени и **ветку исходников или зарегистрированную рабочую папку**. Ветка команды может отличаться от ветки исходников. Для handoff используйте зарегистрированные target и Drive/result bindings из отдельного скила. При необходимости прочитайте манифест и инструкции проекта. Не выводите регистрацию из примера или названия. Для просмотра статуса не запускайте новую задачу.
2. Прочитайте весь **текущий** mailbox и SHA GitHub blob либо полный выбранный native Docs tab и ревизию документа. Не перезаписывайте неподтверждённый `READY`. Сохраняйте поля протокола и идентичности, текущий `slot_token` и принадлежащий Runner `receipt`. `ACK_UNKNOWN`, `NEEDS_RESUBMIT` и прерванные задания требуют сверки, а не автоматического повтора.
3. Подготовьте и проверьте полный `DRAFT` по актуальной схеме. Используйте `request_id: null`, если это разрешено, либо новый UUID; новое намерение требует нового явного ID. Условно запишите DRAFT в точную ветку/путь с наблюдаемым SHA либо точный Docs tab с `requiredRevisionId` и прочитайте обратно. Для Docs используйте native tab indexes фактического API, не длину видимого текста. Полный выбранный tab должен разбираться как один JSON-объект без fences и лишнего текста.
4. **Отдельной последней условной записью** измените только `dispatch` на `READY` с последним SHA blob либо точной ревизией Docs. У `batch_update_document` аргумент коннектора — `write_control.requiredRevisionId`; допускающая слияние подсказка недостаточна. Каждое изменение содержимого адресуйте зарегистрированному tab, сохраняя другие tabs. При конфликте заново прочитайте и согласуйте состояние. Без реальной условной записи сохраните draft и сообщите заблокированный этап; не утверждайте отправку и не используйте скрытый локальный отправитель.
5. Прочитайте ACK mailbox Runner и проверьте токен принятого слота, ID запроса и статус. `READY`, успешная удалённая запись и `ACCEPTED` **не** доказывают завершение, успешные тесты или доставку файлов. ACK может освобождать слот, пока запрос остаётся в существующей FIFO v2. Терминальный результат читайте отдельно; отсутствие/неопределённость ответа требует чтения той же идентичности, а не повторной отправки.

Для `STATUS`, `CANCEL` и `REDELIVER` используйте отдельно разрешённую новую отправку и точный ID целевого запроса по текущей схеме. Повторная доставка использует исходный неизменяемый архив и ветку без повторного исполнения. Не создавайте модельные циклы, API-клиент, скрытый вызов Codex, новые секреты или незарегистрированный shell.

## Доказательства и восстановление
Для `DELIVER_HANDOFF` следуйте [отдельному скилу](../deliver-handoff-to-runner/SKILL.ru.md): читайте точный отдельно зарегистрированный result Doc/tab и сопоставляйте terminal `cdr-handoff-state/1` с request/handoff. Сохраняйте receipt Runner в mailbox. Отдельно сообщайте доставку файлов и доступность ответа, возвращайте только фактический доставленный Codex entrypoint/prompt. Не переносите на эту операцию предположения об исполнении, качестве и Git-результатах.

Читайте отчёт в **проверенной исходной ветке** по пути `.runner/results/<runner_id>/<request_id>/` либо через реально доступное авторизованное локальное чтение. Сверьте `source.json` (исходный SHA и замороженный набор), `result.json` (статус операции, исполнение, quality gate, завершение процессов), `tests.json`, обязательные файлы и нужные логи. Ошибка тестов проекта не равна ошибке инфраструктуры Runner. Отдельно описывайте подготовку, ACK, исполнение, качество, публикацию и доступность, с точными ID/коммитом/ссылками; непройденное отмечайте `NOT_RUN`.

Для GitHub-команд установленного Runner **0.3.0.dev2 или новее** сначала прочитайте **квитанцию о конечном состоянии** `.runner/state/<runner_id>/<request_id>.json` в **ветке командного файла**. В ней есть конечный статус, очищенный код ошибки, результат исполнения/проверок и актуальное состояние доставки; для управляющих команд — данные целевого запроса. Это отдельный документ, не первоначальный ACK; он появляется и при ранней ошибке без тестового архива. Отчёты `.runner/results/<runner_id>/<request_id>/` читайте в **проверенной ветке исходников**.

Неизменяемый `result.json` — **снимок до доставки**: `LOCAL_ONLY / PUBLICATION_PENDING` может сохраняться после фактической публикации в GitHub. Проверяйте актуальную квитанцию состояния или реальные файлы GitHub. Поле `delivery` квитанции относится к пакету результатов, не к самой квитанции. В старой версии 0.3.0.dev1 тест обнаруживал предупреждения `FORMAT_NOT_REGISTERED` для обычных stdout/stderr; в 0.3.0.dev2 добавлен обработчик непрозрачных сырых логов. Не переносите это историческое замечание на новую установленную версию без проверки.

**Граница версий (20.10.2026):** старая 0.3.0.dev1 иногда оставляла ранние ошибки и результаты `STATUS` только локально. В установленной 0.3.0.dev2 реально проверена публикация GitHub-квитанций при успехе, раннем сбое и `STATUS`; см. [проверку на установленном сервисе](../../../../verification/implementation/GP-07/remote-state-20261020/live.json). Если квитанция отсутствует в старой версии или при сбое GitHub, состояние **неизвестно из GitHub** — это не доказательство успешного или продолжающегося исполнения. Проверяйте доступный локальный UI/API, сверяйте последствия и не дублируйте неопределённый запуск.

Отдельный сквозной тест владельца от 20.10.2026 подтвердил цикл Python/Linux: успех → намеренный провал → исправленный успех; исходный тестовый репозиторий приватный. [Публичная проверка версии 0.3.0.dev2](../../../../verification/implementation/GP-07/remote-state-20261020/live.json) подтверждает квитанции успешного запуска, ранней ошибки и ответа STATUS, но не нагрузку, перезапуски, другие ОС и все сценарии отказа.

Для многоэтапной реализации с приёмкой Udot и синхронизацией используйте [execute-roadmap-via-chat-runner](../../udot/execute-roadmap-via-chat-runner/SKILL.md). Этот скил не разрешает планировщику чата отправлять команды Runner.
