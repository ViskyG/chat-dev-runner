# Дизайн: DELIVER_HANDOFF / передать пакет в проект

## 1. Цель и предмет операции

Убрать ручное «скачать архив из чата → найти проект → положить → распаковать → написать Codex».
Не смешивать это с запуском проекта, применением патча, публикацией кода или автоматическим запуском агента.
Handoff — адресованный пакет передачи работы: материалы + точка входа + подтверждённое расположение.

Для этой операции подготовка .runner/project.json и исполнительного SDK не обязательна: достаточно
регистрации проекта, канала и разрешённой папки доставки. Не связывать HANDOFF readiness с RUN_TASK readiness.

## 2. Путь пользователя

1. В чате уже выбран проект. Если у него один default target, повторно спрашивать папку не нужно.
   Несколько равноправных targets или несколько редакторских копий требуют выбора до записи.
2. Чат формирует архив/файлы, SHA-256 и точку входа. Пакет может иметь advisory base_commit,
   но доставка не переключает ветку и не отказывает лишь потому, что разработка ушла вперёд.
3. Скилл проверяет доступность реальной загрузки в Drive и условной записи Docs, регистрацию
   runner/project/target и новый action в installed capabilities. Нет action — не использовать SHELL как обход.
4. Загружает обычный файл, сохраняет фактические ID, версию, размер. Не конвертирует ZIP в Google Doc,
   не публикует файл «по ссылке», не передаёт sandbox:/, file_id ChatGPT или временный bearer URL локальному Runner.
5. Сохраняет полное DRAFT-тело в точном документе/вкладке. Сохраняет текущий slot_token/receipt v2.
   После полного readback отдельной условной записью меняет dispatch на READY. Конфликт — перечитать,
   а не перетереть. ACK — только приём. Доставка завершается локальным подтверждением, не ACK.
6. Runner проверяет локальную регистрацию и адрес; скачивает bytes в staging; проверяет хеш/версию;
   сохраняет оригиналы; по флагу распаковывает ZIP в отдельное пространство; создаёт trusted START_HERE.
7. Публикует новый каталог целиком; фиксирует подтверждение; доставляет краткий результат в отдельный
   зарегистрированный output Doc и обычный v2 state channel (если он доступен). Локальные абсолютные
   пути публикуются только при отдельной политике; обычный результат содержит путь относительно target.
8. Пользователь получает «доставлено в X, начни с Y» и готовую строку Codex. Никакой запуск Codex не происходит.

## 3. Адрес назначения — локальная регистрация

`project_id + target_id` однозначно разрешаются в стабильную рабочую папку или проектную inbox-папку.
Это НЕ временный per-run checkout из SourceResolver и не bare source.git. GitHub-only project может не
иметь локального редакторского target; возвращаем HANDOFF_TARGET_NOT_CONFIGURED, не клонируем самовольно.

Предлагаемое дополнение owner-local enrollment: для проекта хранить `handoff_targets` с workspace_id,
разрешёнными intake folder IDs, локальными лимитами и одним optional default. Никаких absolute paths в COMMAND.
Первое локальное подключение создаёт owner-private inbox и отмечает её служебным пространством.
Повторная доставка в уже разрешённый target не требует нового согласования каждого файла.

Исключить `.runner/handoffs/**` и staging из snapshots, dirty-overlay capture, context inventory, команды
сбора исходников и публикации результатов. Настроить исключение Git локально при enrollment или явно
согласованным изменением .gitignore; remote handoff не имеет права менять эти файлы. Если inbox уже
отслеживается Git, сообщить конфликт регистрации, не скрывать существующие tracked-файлы.
Не делать выдачу из inbox автоматическим фактором запуска watcher/build проекта.

## 4. Новый запрос, существующий v2 канал

Предлагается `request.action = DELIVER_HANDOFF`, `request.handoff` по cdr-handoff/1. Это новый тип данных,
не поле execution и не RUN_TASK. Текущая схема v2 его НЕ поддерживает. Расширять и объявлять action только
в реально зарегистрированной версии/проекте. Старые действия/слоты должны продолжать работать.

Идентичности:
- request_id — принятие конкретного запроса и текущий v2 жизненный цикл;
- handoff_id — стабильный ID доставляемого пакета между проверками и явными попытками восстановления;
- manifest_sha256 — точные данные пакета, без mutable slot_token/receipt.

В текущем v2 уже есть единая durable lane/FIFO. Не переделывать её по старому сентябрьскому запрету очередей.
Первая интеграция маршрутизирует передачу через существующий worker с отдельным handler, не запускающим
executor. CANCEL/STATUS остаются отдельными контролами. Не добавлять второй сервис, скрытый poller или
вторую очередь. Чат не организует автономную цепочку «результат → исправление → следующий запуск».

## 5. Как хранить

Каждый handoff — новый UUID-каталог под .runner/handoffs. Старые версии не перезаписывать.
Оригиналы и распакованное содержимое разделены. Распаковка каждого ZIP в свой namespace по artifact_id:
два архива с README.md не конфликтуют. Не убирать top-level директорию архива автоматически.
Нестандартные .tar/.7z/.rar можно сохранить как непрозрачный файл; авто-распаковка в первой версии только ZIP.
Вложенные ZIP не распаковываются рекурсивно. Нулевые файлы допустимы. Симлинки/специальные ZIP-записи запрещены.
Режимы исполнения, owner/group и xattrs не переносятся. Файлы материалов создаются 0600, папки 0700.
Корневой AGENTS.md существующего проекта не меняется; одноимённый файл внутри payload остаётся материалом.

## 6. Ограничения и проверка

Предлагаемые начальные локальные бюджеты: до 16 входов, 64 MiB каждый, 128 MiB суммарно;
ZIP: до 4096 записей и 512 MiB распакованных байтов на весь handoff, глубина 16, ratio 200.
Это не лимиты Google: локальный владелец может изменить их после проверки. Скилл читает актуальные бюджеты.
В production нужны также общий лимит inbox, свободный резерв диска, bounded streaming/timeout Google,
счётчик реального распакованного объёма, ограничение памяти при чтении ZIP central directory.

Хеш вычисляется в чате по созданному файлу и повторно на компьютере. Drive version проверяется до/после
скачивания. Версия Drive — не revisionId нативного Docs. SHA-256 задаёт идентичность байтов, но не авторство.
Смена Drive metadata version при тех же байтах консервативно требует нового запроса/явного readback.
Права runner и chat app на один Drive-файл проверяются отдельно. Shortcut/native Doc в blob-поле запрещены.

## 7. Отказы и восстановление

| Ситуация | Поведение |
|---|---|
| Неизвестный project/target или смена локальной привязки | Отказ до скачивания и до создания финального каталога. |
| Drive file вне разрешённой intake папки | Отказ, никаких URL-follow или обхода прав. |
| Изменилась версия, размер или SHA-256 | Удалить staging при штатном отказе; не публиковать пакет. |
| Плохой ZIP/entrypoint/лимит | Не распаковывать поверх проекта; финальной доставки нет. |
| Тот же handoff_id и тот же manifest, сохранённые байты целы | Вернуть существующее подтверждение, не скачивать и не выполнять повторно. |
| Тот же handoff_id с другим payload | HANDOFF_ID_CONFLICT; исправление — новый пакет/ID. |
| Пользователь изменил полученные файлы | HANDOFF_CHANGED; не перезатирать работу «восстановлением». |
| Отмена до финальной публикации | CANCELLED, убрать только свой staging. |
| Отмена/обрыв после локальной публикации | Пакет остаётся; отражать локальную доставку и отдельный сбой receipt. |
| Restart после rename до записи DB | Прочитать известный exact path/manifest/inventory и сверить intent; не скачивать повторно автоматически. |
| Receipt upload не прошёл | Local=DELIVERED, remote=FAILED/PENDING; повторить только отправку статуса по разрешённому control. |

Локальное ядро использует неблокирующий lock target и atomic rename-noreplace. Это не distributed exactly-once:
журнал допуска/предварительного намерения, final commit и remote receipt нельзя считать одной транзакцией.
Положительное чтение уже опубликованного receipt допускает reconciliation; отсутствие файла не доказывает,
что предыдущий скачивающий процесс остановлен. Осиротевший .pending не отображается как доставленный.

## 8. Интерфейс

В карточке проекта — «Входящие пакеты». Строка: название, назначение, дата, target, размер,
локальная доставка и состояние возврата подтверждения. Не показывать PASS/тестовые проценты.
Кнопки: «Открыть папку», «Открыть в VS Code» с точным workspace, «Скопировать инструкцию Codex»,
«Состав и контрольные суммы». Нет кнопки «выполнить архив» в этой функции.
Последний пакет можно показать в существующей истории операций без новой KPI-панели.
Состояния этапов: проверка → скачивание (полученные байты) → распаковка → установка → подтверждение.
Нет выдуманных ETA и прогресса до получения измерений.

## 9. Самозагрузка

Пока расширение не интегрировано, этот комплект нельзя доставить его же несуществующей командой.
Первый раз владелец передаёт пакет Codex обычным способом. После квалифицированного внедрения
следующие архивы пойдут через handoff route. Передача архива, меняющего сам Runner, не даёт прав
автоматически обновить или перезапустить работающий Runner.
