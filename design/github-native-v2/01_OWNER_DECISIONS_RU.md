# Окончательные решения владельца
Дата фиксации: 15 октября 2026. Последние ответы в текущем диалоге имеют приоритет над ранним исследованием и над прежними запретами в проекте. Это требования к будущей версии, не описание уже установленной.

## Что должно получиться
**Раннер автономен.** Любой агент или человек может отправлять структурированные задания через управляющий файл GitHub или Google Doc. Google и ChatGPT не обязательны. Никаких локальных команд/кнопок для отправки, подтверждения, отмены или чтения результата. Первоначальная установка и настройка учётных данных на машине — отдельный необходимый этап, не часть каждой отправки.

**GitHub.** Подключается существующий репозиторий и назначенная ветка команд. Команда может выбирать другую ветку этого же подключённого репозитория для проверки. Участники с правом записи могут управлять командным файлом; отдельные роли операторов и обязательный управляющий репозиторий не вводятся. Конкретный `runner_id` обязателен. Одно подключение не означает поиск команд во всех ветках и репозиториях.

**Google Docs.** Один существующий командный документ — один переиспользуемый слот. Автор редактирует DRAFT и последним действием ставит READY. Раннер сам снимает READY при приёме; пользователь/чат видит ACCEPTED и может готовить следующую команду. Позднее завершение старой операции не меняет новую команду. Создание множества документов ради офлайн-очереди не требуется.

**Очередь только живого приёма.** Если раннер выполняет задачу и видит новую отправку, он её принимает в локальную FIFO-очередь. Выполняется одна задача на экземпляр. Не сканировать историю для накопления заданий, созданных в отсутствие раннера. Старые READY не запускать автоматически после старта. Это отменяет раннее решение о долговременном офлайн-накоплении.

**Текущий код.** При начале каждой задачи брать текущую версию выбранной ветки/рабочей области, затем фиксировать неизменяемый снимок на весь запуск. Не использовать версию на момент написания или принятия команды как неявный target. Удалённая ветка означает актуальный успешно fetched HEAD; локальная область — явно выбранное текущее содержимое. Не смешивать эти два источника.

**Исполнение.** Обычные операции test/build/run и явно заданная shell-команда. Нативно от обычного пользователя, запускающего раннер. Не создавать обязательного отдельного системного пользователя и не требовать контейнер для shell. Контейнер — явная опция, не скрытая замена. Нативный режим не является песочницей: код имеет возможности этого пользователя; ограниченный env не делает его изолированным.

**Результаты.** В тот же репозиторий и ту ветку, которая проверялась, в отдельную папку. Включать тесты, результаты программы, диагностические логи, описание среды и точную идентичность проверенного снимка. Не создавать вместо этого служебную результатную ветку, PR, Release/LFS или внешнее хранилище без нового решения владельца.

**Большие/непубликуемые файлы и сбой записи.** Сохранить рядом локально. В доступном отчёте указать причину, машину, точный путь, размер и хеш. Если GitHub совсем недоступен, нельзя утверждать, что предупреждение опубликовано: оно остаётся локально и в других реально доступных настроенных каналах. Не запускать бесконечную доставку и не повторять вычисление ради неё.

**Платформы.** Проверять реальное исполнение на Windows, macOS и Linux. WSL и Linux-контейнер на Windows не засчитывать как нативную Windows-проверку. Пять языков: Python, JavaScript, TypeScript, Java, C#. Compose — после ядра, Unity — последняя ступень.

**Изменения проектов и установка.** Сначала в чате список каждого необходимого изменения: что, где, зачем, что без него, риски, как вернуть назад. По каждому предложить временное обратимое изменение, когда возможно, и получить личное одобрение. Не считать просьбу «подготовить проект» разрешением всех изменений. Одобрённый run может создавать собственное окружение/результаты в предусмотренных каталогах; это не требует нового согласования каждого временного файла.

## Явные инженерные трактовки, принятые в этом пакете
1. Уже принятые задания журналируются надёжно, но очередь действует в одной сессии раннера. После перезапуска незапущенные задания получают `SUSPENDED_RESTART`, а не автоматически продолжаются. Для нового исполнения — новая READY-отправка. Это выбранная трактовка «очередь есть только если раннер жив», которую нельзя скрывать от пользователя.
2. При старте/утрате непрерывности наблюдения текущий слот становится базовой точкой. Старый READY получает NEEDS_RESUBMIT. Автор может повторно отправить его прямо в том же документе/файле. История не читается для восстановления очереди.
3. «Сохранить рядом» = соседний `runner-results/` в управляемом каталоге проекта, вне исходников. Точный путь публикуется только для непереданных файлов и только в назначенном репозитории/канале; хостовые секреты и env-дампы туда не попадают.
4. Передача управления всегда остаётся документной/файловой. CAS и служебные идентификаторы обслуживает программа; человеку не предлагается вручную запускать CLI, вычислять хеши или придумывать UUID.

Это не новые вопросы владельцу. Это явно отмеченные детали проектирования, вынесенные также в тесты и handoff.

## Что отменено
NO QUEUE / terminal BUSY вместо ожидания; офлайн-журнал `one file per request` с историческим replay; fixed SHA at admission; results-only branch; обязательный Drive; обязательный отдельный OS-пользователь; контейнер как единственное исполнение; обязательная повторная доставка; автоматический LFS/Releases; локальная кнопка отправки.
